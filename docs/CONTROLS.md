# Negative controls and diagnostics (`KAROO_*_FX`, `KAROO_*_DIAG`)

Every env-var mode that makes a replacement's effect observable. The *principles* for
designing one live in CLAUDE.md ("Verify visually, not just in logs"); this is the
catalogue. Add a row when you add a mode. Plan documents (GAMETICK_PLAN.md,
RENDER_PLAN.md, PARTICLE_PLAN.md) hold the full story behind each result.

| Mode | Proves |
|---|---|
| `KAROO_PARTICLE_FX=antigrav` | gravity integration (particles rise) |
| `KAROO_PARTICLE_FX=burst` | emission (x3 initial velocity) |
| `KAROO_PARTICLE_FX=loadflip` | environment `Load` (slot 5): negates the loaded gravity magnitude and magnet force, so falling effects rise and magnets repel |
| `KAROO_PARTICLE_FX=fastemit` | generator `Load` (slot 5, Std/XStd/Cylinder): x5 the loaded emit rate. Moves a counter, not a coordinate, so it is safe for `levelreport.py` |
| `KAROO_PARTICLE_FX=tint` / `spin` | render fill / XFace tick |
| `KAROO_FAKTMESH_FX=half` | mesh draw |
| `KAROO_TEXTURE_FX=solid` | SceneTexture loaders (fills every texture magenta) |
| `KAROO_TEXTURE_FX=bpp16` | SceneTexture format choice — *logs* the chosen format; **not visible on screen**, see RENDER_PLAN.md |
| `KAROO_TEXTURE_FX=deepfmt` | `EnumTextureFormatsPickerCallback` (`scenetexture.cpp`, ENDGAME_PLAN.md E1); reverses the format preference — among the formats at or above the requested depth, keep the one **furthest** above it instead of the closest.  A direction change, and one nothing else in the binary can make: this callback is the only code that chooses a texture format.  Bounded to a pixel format, so it moves no geometry and cannot reach the bridge/slide spawn scans.  **Neither gate can see it** — the suite passes 16/16 either way.  Live, and proven by value: the chosen format goes `32bpp a=FF000000` -> `16bpp a=0000F000`, i.e. ARGB8888 -> ARGB4444.  That outcome was *predicted from the rules before the run*, which makes it arithmetic proof rather than liveness — under `deepfmt` the ladder climbs 16-555 -> 16-1555 -> 16-4444 and stops, because the equal-depth alpha fallback needs `bits == kept` and 32 != 16.  Live-but-unobserved, like `KAROO_TEXT_FX=bigwave` and `KAROO_LIST_FX=lifo` |
| `KAROO_IMAGE_FX=gamevtbl` | the `LoadedImage` / `SceneTexture` ctor and dtor bodies (`texture.cpp`, `scenetexture.cpp`, ENDGAME_PLAN.md E1/E2); installs the **game's** vtable address (`0x0045d708` / `0x0045d71c`) instead of our own one-slot tables.  Those slots point at UD2-stubbed originals, so anything dispatching through the table faults.  It answers a question rather than perturbing a value — a clean run would say nothing reads the table, a fault says our table is load-bearing and names the reader.  **Both gates see it, and hard**: the suite goes **0/16** with 9 `c000001d`, every recording failing on "crash classification differs" and "no dump was written", not on `frames_run` +1.  So vtable dispatch on these objects is real and constant, and this is a control that can fail rather than one that can only pass |
| `KAROO_IMAGE_DIAG=1` | census over all six `LoadedImage`/`SceneTexture` ctor/dtor entry points (`texture.cpp`, `scenetexture.cpp`), plus each `CreatePaletteFromDIB` call with its colour count and flags.  Each announces its **first call** — the two scalar deleting dtors are the ones worth watching, since neither has a single CALL or JMP anywhere in the binary and each is reachable only through vtable slot 0.  Across the full replay suite **five of the six are reached, in exactly the two chains the replacement claims**: `SceneTexture::Constructor` -> `LoadedImage::Ctor` on the way in, and `SceneTexture::ScalarDeletingDtor` -> `SceneTexture::DtorBody` -> `LoadedImage::DtorBody` on the way out.  The scalar dtor being reached is what `gamevtbl` crashing on, corroborating it from the other side.  `LoadedImage::ScalarDeletingDtor` is **never called** by either gate — verified by decompile and by our table's slot 0, not by test, exactly as `LinkedList::ScalarDestructor` is.  `CreatePaletteFromDIB` logs nothing either: nothing the suite loads is 8bpp or less |
| `KAROO_SOUND_FX=gamevtbl` | the `CStaticSoundbuffer` / `CStreamSoundbuffer` ctors and re-init bodies (`static.cpp`, `stream.cpp`, ENDGAME_PLAN.md E2); installs the **game's** vtable address (`0x0045ef9c` / `0x0045efa4`) instead of our own one-slot tables.  The `KAROO_IMAGE_FX=gamevtbl` measurement applied to the sound objects: both slots point at UD2-stubbed originals, so any dispatch through the table faults.  **The suite goes 0/16 with 9 `c000001d`** — every recording, not a subset — so dispatch through these two tables is real and constant, and this is a control that can fail rather than one that can only pass.  Blast radius is one pointer field per object: no geometry, so `levelreport.py` can host it too |
| `KAROO_SOUND_DIAG=1` | census over both sound classes' destructor entry points (`static.cpp`, `stream.cpp`).  Each announces its **first call**, never a periodic sample.  **Both are reached** by the replay suite (`CStaticSoundbuffer::ScalarVectorDtor`, then `CStreamSoundbuffer::ScalarDeletingDtor`), which is what `gamevtbl`'s 0/16 corroborates from the other side — and it overturned the assumption written into ENDGAME_PLAN first, that a slot-0 dtor with no `CALL` or `JMP` anywhere in the binary is unreachable by the gates.  It is not; `LoadedImage`'s being unreached was a fact about that class, not a rule.  Suite passes 16/16 with the census on |
| `KAROO_SCORE_FX=tint\|nodraw` | the end-of-game overlay quads (`scoreoverlay.cpp`) — reach the high-score page with `KAROO_MENU_NODE=3` |
| `KAROO_BRIDGE_FX=tint\|nodraw\|backward` | the scrolling conveyor/bridge quads (`bridgesurf.cpp`); `backward` reverses the scroll — a direction change |
| `KAROO_BRIDGE_DIAG=1` | logs each distinct bridge `(conveyor, axis, dir, n)` variant once with its `v` coordinates — how to tell "that orientation is not drawn here" from "that orientation is mismapped" |
| `KAROO_D3DDEV_FX=mode0\|halfvp` | `Direct3D::CreateD3DDevice` (`createdevice.cpp`); `mode0` forces mode index 0 so the game comes up in a different **resolution** — a measured change, not a colour |
| `KAROO_D3DDEV_FX=firstzbuf` | `EnumZBufferFormatsCallback` (`createdevice.cpp`, ENDGAME_PLAN.md E1); keeps the **first** `DDPF_ZBUFFER` format the driver offers instead of the deepest one, by dropping the callback's `src >= dst` depth comparison.  That comparison is the only thing that chooses between the offered formats, so the device is built on a different z-buffer — a decision nothing but this callback makes.  Bounded on purpose: it moves no geometry, so it cannot reach the unguarded bridge/slide spawn scans.  **Neither gate can see it** — the suite passes 16/16 either way, because nothing the recordings assert is downstream of the z-buffer's depth.  Live, and the DIAG says so by value: `zfmtKept` falls 3 -> 1 and the device is built with `zdepth=16 stencil=0` instead of `32`/`8`.  Live-but-unobserved, like `KAROO_TEXT_FX=bigwave` and `KAROO_LIST_FX=lifo` |
| `KAROO_D3DDEV_DIAG=1` | census over the three helpers `CreateD3DDevice` owned outright (`createdevice.cpp`): display modes seen and kept, z-buffer formats seen and kept, and `Direct3D::Log` lines.  They run only while the device is built and what the gates assert is game state, so this is the only way to tell "ran and agreed" from "never ran".  A headless run reports `modesSeen=93 modesKept=16 zfmtSeen=4 zfmtKept=3 logLines=0` — the mode filter keeping 16 of 93 and the z-buffer ladder climbing to the deepest of 4 are positive proof by value.  **`logLines=0` is a finding**: all fourteen `Log` call sites are error paths, so on a device that comes up it is never entered — reimplemented, correct and unreached in this build |
| `KAROO_CAM_DIAG=1` | logs the camera globals at 0x46c4a0 (eye, target, yaw, pitch; raw bits) every frame from `Scene_DrawSceneObjects` (`dsoscene.cpp`), which `RenderGameFrame` reaches after `UpdateViewTransform` whichever implementation ran.  **An oracle for `camera.cpp`**: withdraw its three `patch.py` entries (the CALL and both UD2s) to run the original, diff the two logs with the timestamp column cut.  2026-09-25, castle-something `--no-fast`: 1031/1031 frames bit-identical, yaw across 0..2pi, pitch to 1.564.  Watched fail: the grid rounding 0.5 -> 0.45 moves 183 frames **and the replay suite still passes** -- no gate sees the camera  Also logs the `CameraFocus` block (0x4e01a0) and an FNV hash of the foe pose records (0x4dc7c8) for `framepose.cpp`: 3093/3093 lines identical; a 1% step-fraction perturbation moves CAM, FOCUS and FOES lines |
| `KAROO_D3D_FX=wire\|tint\|light\|nodraw` | COM proxy layer; `nodraw` returns D3D_OK from all six `DrawPrimitive*` without forwarding — a speed switch, not a visual one (see `replaytest.py --fast`) |
| `KAROO_CRT_FX=seed` | the level seed store in `Sim_SetupLevelObjects` (`levelsetup.cpp`) now that it is our `crt_srand()` and not the game's `srand` (CRT_PLAN.md Stage A); flips the seed's low bit. **Neither gate can see it** — the suite still passes 16/16, because nothing the recordings assert is downstream of this seed. Live-but-unobserved; use the DIAG below for liveness |
| `KAROO_CRT_FX=path` | our `sprintf` building the level/script paths (`levelparse.cpp`, CRT_PLAN.md Stage C); swaps the two `%s` arguments so the path becomes `<name>\Levels\<gamedir>`. Breaks a pure function's **structure** rather than a value, and unlike the other two CRT controls a gate sees it — every recording fails at load |
| `KAROO_CRT_DIAG=1` | two CRT censuses, both for things no gate can see. **Stage A:** logs `crt_srand()`'s argument and reads back the game's seed global `0x00469f38` — the check the libc `srand()` would have failed. **Stage B:** logs `STD_ERROR_HANDLE` (NULL here), the game's live `_iob[2]` `_flag`/`_file`, and what our `fwrite(stderr)` returns — the evidence that `0x00469cf8` is `stderr` and that our writes and the game's name the same fd |
| `KAROO_LIST_FX=lifo` | the game's generic `LinkedList::Append` (`linkedlist.cpp`, ENDGAME_PLAN.md E1); links each new node at the **head** instead of the tail, so every list in the game iterates in the opposite order.  **Neither gate can see it** — the suite still passes 16/16.  It is *live*, not dead: `list_fx()` is reachable only from inside `List_Append`, so the `FX mode = lifo` log line is itself proof that Append ran with the links reversed.  Nothing the recordings assert is downstream of list order.  Live-but-unobserved, like `KAROO_CRT_FX=seed`; use the DIAG below for coverage |
| `KAROO_LIST_DIAG=1` | census over all seven `LinkedList` functions (`linkedlist.cpp`).  Each announces its **first call**, and Append dumps a running tally at 1/100/1000/10000 then every 20000 — the periodic sample alone would read zero forever for anything first reached after the last threshold, which is the very mistake a census exists to avoid.  How to tell "the suite never calls `Unlink`" from "the suite calls `Unlink` and cannot see it" |
| `KAROO_POOL_FX=onevoice` | `VoicePool::VoicePoolFill3D` / `VoicePoolClone` (`voicepool.cpp`, ENDGAME_PLAN.md E1); clamps every pool to a **single voice** whatever count the caller asked for.  That is the one thing this class decides outright, and it is a real change of outcome rather than a perturbation: a pool exists so a sound can overlap itself, and `VoicePoolCycle` halts and re-triggers the *same* slot each call, so a one-voice pool can never overlap.  Bounded on purpose — it allocates DirectSound buffers and moves no geometry, so it cannot reach the unguarded bridge/slide spawn scans that crash `levelreport.py`.  **Neither gate can see it** — the suite passes 16/16 either way, because nothing the recordings assert is downstream of how many voices a sound has.  Live, and proven by value with the outcome *predicted before the run*: over `water01` the DIAG's `voicesAllocated` falls **60 -> 11** across the same 11 `Clone` calls, and every other counter is byte-identical (`blank=11 wipe=26 getvoice=13 firstname=13 cycle=363 broadcast=357`).  Eleven pools, one voice each, is exactly what the control asks for.  Live-but-unobserved, like `KAROO_TEXT_FX=bigwave` and `KAROO_LIST_FX=lifo` |
| `KAROO_POOL_DIAG=1` | census over all eight `VoicePool` functions (`voicepool.cpp`).  Each announces its **first call**; the three cold entry points (`Fill3D`, `Clone`, `Wipe`) then dump the full tally, including `voicesAllocated`, `copyFallbacks` (a duplicate DirectSound refused, so the voice was reloaded from the file) and `nestBails` (the re-entrancy guard tripping — which is how the dead software-retry defect shows itself).  No sampling threshold: pools are built a handful of times per level load, not per sound, so unlike `KAROO_LIST_DIAG` every call can report |
| `KAROO_DSB_FX=stickyentry` | the sound-asset entry's lifetime predicate `EntryIsFullyReleased` (`doublesoundbuff.cpp`, ENDGAME_PLAN.md E1); always answers **no**, so no loaded sound is ever torn down when its last borrower leaves.  That predicate is the one thing this TU decides outright — nothing else in the game asks whether an asset may die — and forcing it false changes an *outcome*, not a value: every file stays resident once loaded.  Chosen for blast radius too: it can only ever leak, never free something still in use, so unlike a coordinate control it cannot reach the unguarded bridge/slide spawn scans that crash `levelreport.py`.  **Neither gate can see it** — the suite passes 16/16 either way, because nothing the recordings assert is downstream of when a sound buffer is released.  Live, and proven by value with the outcome *predicted before the run*: over `water01` `KAROO_DSB_DIAG` goes `fullyReleased=35/59` -> **`0/59`** — the same 59 calls, not one of them a yes — and `borrowerCount` falls `59 -> 0`, which is the short-circuit showing itself.  The unpredicted cross-check is better still: `clear` rises `63 -> 98`, exactly **+35**, so the 35 entries that used to die on their last release now defer to the bulk purge instead.  Live-but-unobserved, like `KAROO_POOL_FX=onevoice` and `KAROO_TEXT_FX=bigwave` |
| `KAROO_DSB_DIAG=1` | census over all nine `doublesoundbuff` functions (`doublesoundbuff.cpp`).  Each announces its **first call**; `Clear` and `Destruct` then dump the full tally.  No sampling threshold — entries are built a handful of times per level load, not per sound.  Carries `masterLent` / `spareLent`, the two identity paths in `ReleaseCloneOrOwnBuffer` that hand a buffer back without it ever having been on a list, and that pair earns its keep immediately: over `water01` they read **33 and 0**, so the master half of the class is heavily used and the **spare half is never reached at all** — live code and (so far) unexercised code, told apart by value |
| `KAROO_SNDMGR_FX=nosharemaster` | the sound manager's one outright decision, `dwMasterTaken` (`soundmanager.cpp`, ENDGAME_PLAN.md E1); the first acquirer of a sound no longer receives the entry's own master buffer, it gets a duplicate like every later one.  Nothing else in the game makes that choice.  **Bounded on purpose, and the contrast with `KAROO_NAMEDLIST_FX=nofind` is the point**: sharing still works and the entry is still found, so the cost is one extra DirectSound duplicate per distinct sound rather than an unbounded list.  Safe to run under `levelreport.py`, and it was.  **Neither gate can see it** — 16/16 and a matching level report either way, because nothing the recordings assert is downstream of which copy of a buffer a caller holds.  Live, and proven by value with every number *predicted before the run*: over `water01` `masterGrants` goes **43 -> 0** and `clones` **23 -> 66**, a rise of exactly the 43 that used to be granted, while `acqStatic=66 (hit 66 new 43)`, `acqPool=11`, `relStatic=52`, `relPool=7` and `destroyed=35` are byte-identical.  The best evidence is in a census this cycle did not write: `KAROO_DSB_DIAG`'s `masterLent` falls **33 -> 0**, because the master is what `ReleaseCloneOrOwnBuffer` recognises by identity.  And one unpredicted cross-check, stronger than the aimed-at counter: `acqSpare` falls **11 -> 0** and `load` **54 -> 49**, so the spare-buffer fallback is taken *only* when the master has been lent out — two counters that were not designed to be related, moving together |
| `KAROO_SNDMGR_DIAG=1` | census over all six replaced `SoundManager` entry points (`soundmanager.cpp`).  Each announces its **first call** — and this is the first cycle in this band where **every** function is reached by the suite, unlike `VoicePool::Fill3D` or the three slot-only destructors.  The tally dumps from the two releases and from `setup` (cold paths) and from the acquire path (so a run that never releases still reports).  Its value is cross-census agreement: over `water01` the entries it creates (`new 43` + `new 6` = 49) equal `KAROO_NAMEDLIST_DIAG`'s `insert=49` and `KAROO_DSB_DIAG`'s `init=49`; its `destroyed=35` equals their `remove=35` and `fullyReleased=35/59`; and `masterGrants 43 + clones 23 = 66` equals its own `acqStatic=66`.  Four independent counters written in three different cycles agreeing is a much stronger statement than any one of them |
| `KAROO_NAMEDLIST_FX=nofind` | the sound system's identity-by-name, `NamedEntryList::FindByName` (`namedlist.cpp`, ENDGAME_PLAN.md E1/E2); every lookup misses, so no loaded sound is ever shared.  That lookup is the one thing this class decides outright — every acquire asks "is this file already loaded?" and every release asks "which entry owns this buffer?", and nothing else in the game answers either — so this is the property-breaking form CLAUDE.md asks for on a pure function rather than a perturbed value.  **This is one of the very few controls a gate can FAIL on**, and it does: the suite goes 0/16.  Read the failing fields, though, because they do not say what a casual reading suggests — `frames_run` is **2** and every other field is missing, i.e. the run never got past level load.  Proven by value all the same: over `water01` the DIAG goes `find=211 (hit 136) insert=49 maxLen=36` -> `find=40000 (hit 0) insert=40000 maxLen=39999`, every single lookup a miss and a list growing without bound.  **Blast radius exceeds what a state gate can interpret, and that is the finding**: this class's only outright decision is also what BOUNDS the sound system's growth, so a control on it cannot itself be bounded.  Do not run `levelreport.py` under it — it would do the same thing eighty times.  Zero `c000001d` throughout, so nothing reached a stub |
| `KAROO_NAMEDLIST_DIAG=1` | census over all seven `NamedEntryList` functions (`namedlist.cpp`).  Each announces its **first call**; the tally then dumps from `Clear` (the cold path, after the frees, so it reflects the end state) **and** from `Insert` at 1/100/1000/10000 then every 20000.  Both, deliberately: a cold-path-only census goes silent under `nofind`, which is the very condition it exists to measure, and a census that cannot report on its own control is no census.  Over `water01` the clean run reads `construct=2 sdtor=0 dtorbody=2 insert=49 clear=8 (freed 14) remove=35 find=211 (hit 136) maxLen=36`, and the arithmetic is the cross-check the counters were not designed to give: **35 + 14 = 49**, every entry created freed exactly once, by one path or the other.  `sdtor=0` names the gap — `ScalarDtor` is vtable slot 0 and **neither gate ever reaches it**, so its reimplementation is verified by the decompile and by our table's slot 0, not by test, the same status `LinkedList::ScalarDestructor` carries |
| `KAROO_TEXT_FX=mirror` | the bitmap-font glyph loop (`textrenderer.cpp`, ENDGAME_PLAN.md E1); negates the pen advance, so every string lays itself out **right-to-left** from its first glyph — a direction change, chosen over a value perturbation.  The two centring wrappers are untouched on purpose: they keep using the true width.  **Neither gate can see it** — the suite still passes 16/16, because what the recordings assert is game state, not where a glyph landed.  It is *live*, not dead, and unusually well covered: the DIAG below counts 74735 glyphs in a single recording.  Live-but-unobserved, like `KAROO_LIST_FX=lifo` and `KAROO_CRT_FX=seed` |
| `KAROO_TEXT_FX=loadswap` | the `.fon` loader (`textrenderer.cpp`, ENDGAME_PLAN.md E1); stores the atlas grid transposed, columns into rows.  A direction change the loader alone can produce — the glyph loop divides by `cols`, so a transposed grid re-indexes every character.  `font1.fon` is 16x16 and so is its own transpose, so only `numbers.fon` (4x3 -> 3x4) moves; that is a property, not a weakness — it shows the control acts on the *file's contents*.  **Neither gate can see it**: the suite passes 16/16 either way.  Live, and the DIAG below proves it by value |
| `KAROO_TEXT_FX=bigwave` | the wobbling glyph loop `DrawWobbleGlyphRow` (`textrenderer.cpp`, ENDGAME_PLAN.md E1); steps the per-glyph sine phase by **-2 instead of +2**, so the vertical wave travels along the string the other way.  A direction change again, and a tightly confined one: the string keeps its position (the pen advance is untouched), its size (the amplitude is untouched) and its centring (`drawBig`'s wrapper arithmetic is untouched) — only the wave's travelling direction reverses, which nothing but this loop can produce.  **Neither gate can see it**: the suite passes 16/16 either way.  Live, not dead, and the DIAG below says so by value — under `bigwave` the `gameover-forest` recording still reports `wobble=152`, so the loop ran 152 times with its phase reversed.  Live-but-unobserved, like `mirror`, `KAROO_LIST_FX=lifo` and `KAROO_CRT_FX=seed` |
| `KAROO_WRAP_FX=scrollback` | the mesh UV scroll `WrapperObject::ScrollVertexUVs` (`wrapperobject.cpp`, ENDGAME_PLAN.md E2); negates the per-frame delta, so every scrolling texture — water, conveyor stripes — runs **backwards**.  A direction change, and one only this function can make: it is the sole writer of animation mode 6.  Blast radius is a texture coordinate, so unlike a coordinate control it cannot reach the unguarded bridge/slide spawn scans that crash `levelreport.py` |
| `KAROO_WRAP_FX=sineflip` | the mesh UV sine warp `WrapperObject::ApplySineWaveVerts` (`wrapperobject.cpp`); negates the sine term, so the warp travels the other way along both axes while its amplitude, its cosine term and the base coordinates stay put.  A direction change again, tightly confined |
| `KAROO_WRAP_FX=envflip` | the spherical environment map `WrapperObject::UpdateObjectTransform` (`wrapperobject.cpp`); negates the generated `v`, so every reflection is mapped upside down.  Chosen on the *generated* coordinate rather than on the facing test, because flipping the facing test would change **which** vertices are written and that is a bigger blast radius than a direction change needs |
| `KAROO_WRAP_DIAG=1` | census over all eight `WrapperObject` entry points (`wrapperobject.cpp`), and it is the whole verification for this class: what the recordings assert is game state, and nothing this class does leaves the texture coordinates.  Each entry announces its **first call**, then samples every 20000.  It says the class is heavily live: over one suite run `ctor`, `setMesh`, `releaseSnapshot`, `dtor`, `flush` and `updateObjectTransform` all report, the environment map passing **3000 calls** in a single recording with **8.2 million** texture coordinates written between it and the flush.  It also names the gap honestly — `applySineWave` and `scrollUVs` report **no first call at all** in any of the sixteen recordings, so animation modes 4 and 6 are verified by the listing, not by test, and `sineflip`/`scrollback` are controls nothing currently exercises.  One operational note, learned the hard way: at a 1000-call sampling period the logging alone slowed `water01` from 10 s to 21 s and the recording failed on a *missing dump* rather than on a state difference — read the failing fields, because a census dense enough to change the timing is measuring itself |
| `KAROO_TEXT_DIAG=1` | census over the five replaced text entry points (`textrenderer.cpp`), and the strongest evidence in this group: the loader logs **the values it parsed**, `fonts\font1.fon -- 16 x 16` and `fonts\numbers.fon -- 4 x 3`, which are byte-for-byte the two shipped files.  That is positive proof the reimplementation parsed correctly, not merely that it ran.  Each announces its **first call**; `RenderText` dumps a tally of calls, empty strings, glyphs and the two wrappers' counts at 1/100/1000/10000 then every 20000.  How to tell "no gate draws right-aligned text" from "it is drawn and nothing asserts it".  It also carries `big=` / `wobble=` / `wobbleGlyphs=` for the big-text pair, and those three are the positive proof for that cycle: **only `gameover-forest` reaches them**, and it reports `big=152 wobble=152 wobbleGlyphs=1368` — 1368 / 152 = **9**, which is exactly `strlen("GAME OVER")`.  That is an arithmetic cross-check on the glyph loop, not merely a liveness flag |
| `KAROO_SIM_FX=blindfoe` | the foe pathfinder's walkability test (`foepath.cpp`) — every cell reports impassable, so foes stop chasing; **7 of 12 recordings can see it** |
| `KAROO_SIM_FX=keyclash` | the pathfinder's node-key helper (`foepath.cpp`); collapses each map row to one key — a pure function whose control must break **injectivity**, since perturbing the value proves nothing |
| `KAROO_SIM_FX=popsecond` | the pathfinder's open-list pop (`foepath.cpp`); expands the second-best node instead of the best — proves the f-ordering is load-bearing |

| `KAROO_SIM_FX=nocostfix` | the pathfinder's cost cascade (`foepath.cpp`) — skips re-propagation entirely.  **Does not fail the suite**: that subsystem is exercised but unobservable, see GAMETICK_PLAN.md |
| `KAROO_SIM_FX=chaseback` | the foe chase step (`foe.cpp`) — reverses the delta-to-facing table so foes step **away** from the player along the path just found; **9 of 12 recordings fail** |

| `KAROO_FOEPATH_DIAG=1` | counts the pathfinder's re-open machinery — cascades, re-parents, worklist pushes/pops and deepest drain, logged at 1/10/100/1000/10000 cascades.  How to tell "dead code" from "live but unobserved" |
| `KAROO_SIM_FX=nopickup` | the player tick's standing-on-tile gate (`player.cpp`); no tile is ever consumed, so no gems, no items, no timed effects — **11 of 12 recordings fail**, the strongest control in the sim work.  `bridge01` is blind to it: it collects nothing |
