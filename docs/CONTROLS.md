# Diagnostics (`KAROO_*_DIAG`, `KAROO_*_DUMP`)

Every env-var mode that makes a replacement's effect observable.  The negative
controls (`KAROO_*_FX`) that deliberately broke a piece of the game to prove a
gate could see it were removed once the replay suite was established; a row
below that cites one records what was shown at the time.  An on/off switch is
read with `sysdev::envFlag` (on unless unset, empty or starting with `0`). The *principles* for
designing one live in CLAUDE.md ("Verify visually, not just in logs"); this is the
catalogue. Add a row when you add a mode. Plan documents (GAMETICK_PLAN.md,
RENDER_PLAN.md, PARTICLE_PLAN.md) hold the full story behind each result.

| Mode | Proves |
|---|---|
| `KAROO_TEXTURE_DUMP=<file>` | texture upload (`devicetexture.cpp`): appends one line per texture or image surface -- name, size, pixel format, FNV-1a of the bytes.  `tools/texdump.py` collects it over the replays and diffs two runs, so a change to the loaders or the format conversion shows whether one pixel moved.  Records, does not perturb |
| `KAROO_DRAW_TRACE=<file>` | the draw path (`drawtrace.cpp`): one line per draw, hashing the primitive, the vertex bytes and the pipeline state the game has set (`=1` in `KAROO_DRAW_TRACE_VERBOSE` writes the state as text).  `tools/drawtrace.py` collects it over the replays and diffs two runs, so a change to the rendering code shows whether it moved a draw, a vertex or a state.  Needs a real device (`--no-headless`).  Records, does not perturb |
| `KAROO_BRIDGE_DIAG=1` | logs each distinct bridge `(conveyor, axis, dir, n)` variant once with its `v` coordinates — how to tell "that orientation is not drawn here" from "that orientation is mismapped" |
| `KAROO_CAM_DIAG=1` | logs the camera globals at 0x46c4a0 (eye, target, yaw, pitch; raw bits) every frame from `Scene_DrawSceneObjects` (`dsoscene.cpp`), which `RenderGameFrame` reaches after `UpdateViewTransform` whichever implementation ran.  **An oracle for `camera.cpp`**: withdraw its three `patch.py` entries (the CALL and both UD2s) to run the original, diff the two logs with the timestamp column cut.  2026-09-25, castle-something `--no-fast`: 1031/1031 frames bit-identical, yaw across 0..2pi, pitch to 1.564.  Watched fail: the grid rounding 0.5 -> 0.45 moves 183 frames **and the replay suite still passes** -- no gate sees the camera  Also logs the `CameraFocus` block (0x4e01a0) and an FNV hash of the foe pose records (0x4dc7c8) for `framepose.cpp`: 3093/3093 lines identical; a 1% step-fraction perturbation moves CAM, FOCUS and FOES lines |
| `KAROO_NOVSYNC=1` | `GLRenderDevice::Create` (`src/gl/createdevice.cpp`); sets the swap interval to 0 instead of waiting for vsync.  The replay harness sets it (turbo), whichever driver is underneath |
| `KAROO_SCREENSHOT=<prefix>` with `KAROO_SCREENSHOT_FRAMES=<n>[,<n>...]` | `RenderDevice::Present` (`src/gl/renderdevice.cpp`); writes the back buffer of the n-th presented frames, just before they are shown, to `<prefix>-<n>.ppm`.  A screen grab of the full-screen window can come out black (the display server does not always give one); this reads the frame from OpenGL.  Needs a real device (`--no-headless`) |
| F10 | `src/debugui`; shows and hides the Dear ImGui debug overlay, drawn through `RenderDevice::SetOverlay` over each presented frame.  While one of its text boxes has focus the game sees no keys.  Not in headless runs |
| `KAROO_RENDER_FX=nodraw` | `RenderDevice::Draw`/`DrawBuffer` return success without reaching the device — a speed switch, not a visual one (see `replaytest.py --fast`) |
| `KAROO_CRT_DIAG=1` | two CRT censuses, both for things no gate can see. **Stage A:** logs `crt_srand()`'s argument and reads back the game's seed global — the check the libc `srand()` would have failed. **Stage B:** logs `STD_ERROR_HANDLE` (NULL here), the game's live `_iob[2]` `_flag`/`_file`, and what our `fwrite(stderr)` returns — the evidence that the game's `_iob[2]` is `stderr` and that our writes and the game's name the same fd |
| `KAROO_POOL_DIAG=1` | census over all eight `VoicePool` functions (`voicepool.cpp`).  Each announces its **first call**; the three cold entry points (`Fill3D`, `Clone`, `Wipe`) then dump the full tally, including `voicesAllocated`, `copyFallbacks` (a duplicate DirectSound refused, so the voice was reloaded from the file) and `nestBails` (the re-entrancy guard tripping — which is how the dead software-retry defect shows itself).  No sampling threshold: pools are built a handful of times per level load, not per sound, so unlike `KAROO_LIST_DIAG` every call can report |
| `KAROO_DSB_DIAG=1` | census over all nine `doublesoundbuff` functions (`doublesoundbuff.cpp`).  Each announces its **first call**; `Clear` and `Destruct` then dump the full tally.  No sampling threshold — entries are built a handful of times per level load, not per sound.  Carries `masterLent` / `spareLent`, the two identity paths in `ReleaseCloneOrOwnBuffer` that hand a buffer back without it ever having been on a list, and that pair earns its keep immediately: over `water01` they read **33 and 0**, so the master half of the class is heavily used and the **spare half is never reached at all** — live code and (so far) unexercised code, told apart by value |
| `KAROO_SNDMGR_DIAG=1` | census over all six replaced `SoundManager` entry points (`soundmanager.cpp`).  Each announces its **first call** — and this is the first cycle in this band where **every** function is reached by the suite, unlike `VoicePool::Fill3D` or the three slot-only destructors.  The tally dumps from the two releases and from `setup` (cold paths) and from the acquire path (so a run that never releases still reports).  Its value is cross-census agreement: over `water01` the entries it creates (`new 43` + `new 6` = 49) equal `KAROO_NAMEDLIST_DIAG`'s `insert=49` and `KAROO_DSB_DIAG`'s `init=49`; its `destroyed=35` equals their `remove=35` and `fullyReleased=35/59`; and `masterGrants 43 + clones 23 = 66` equals its own `acqStatic=66`.  Four independent counters written in three different cycles agreeing is a much stronger statement than any one of them |
| `KAROO_UVANIM_DIAG=1` | census over all eight `UVAnimator` entry points (`uvanimator.cpp`), and it is the whole verification for this class: what the recordings assert is game state, and nothing this class does leaves the texture coordinates.  Each entry announces its **first call**, then samples every 20000.  It says the class is heavily live: over one suite run `ctor`, `setMesh`, `releaseSnapshot`, `dtor`, `flush` and `updateObjectTransform` all report, the environment map passing **3000 calls** in a single recording with **8.2 million** texture coordinates written between it and the flush.  It also names the gap honestly — `applySineWave` and `scrollUVs` report **no first call at all** in any of the sixteen recordings, so animation modes 4 and 6 are verified by the listing, not by test, and `sineflip`/`scrollback` are controls nothing currently exercises.  One operational note, learned the hard way: at a 1000-call sampling period the logging alone slowed `water01` from 10 s to 21 s and the recording failed on a *missing dump* rather than on a state difference — read the failing fields, because a census dense enough to change the timing is measuring itself |
| `KAROO_TEXT_DIAG=1` | census over the five replaced text entry points (`textrenderer.cpp`), and the strongest evidence in this group: the loader logs **the values it parsed**, `fonts\font1.fon -- 16 x 16` and `fonts\numbers.fon -- 4 x 3`, which are byte-for-byte the two shipped files.  That is positive proof the reimplementation parsed correctly, not merely that it ran.  Each announces its **first call**; `RenderText` dumps a tally of calls, empty strings, glyphs and the two wrappers' counts at 1/100/1000/10000 then every 20000.  How to tell "no gate draws right-aligned text" from "it is drawn and nothing asserts it".  It also carries `big=` / `wobble=` / `wobbleGlyphs=` for the big-text pair, and those three are the positive proof for that cycle: **only `gameover-forest` reaches them**, and it reports `big=152 wobble=152 wobbleGlyphs=1368` — 1368 / 152 = **9**, which is exactly `strlen("GAME OVER")`.  That is an arithmetic cross-check on the glyph loop, not merely a liveness flag |
| `KAROO_FOEPATH_DIAG=1` | counts the pathfinder's re-open machinery — cascades, re-parents, worklist pushes/pops and deepest drain, logged at 1/10/100/1000/10000 cascades.  How to tell "dead code" from "live but unobserved" |
| `KAROO_DECK_DIAG=1` | logs the bridge tick's (`bridgeobject.cpp`) first tick, first extend stamp and first retract unstamp, plus a tick count every 5000 — how to tell "no hazards in this recording" from "hazards that never arm" |
| `KAROO_LIFT_DIAG=1` | logs the vertical lift's first tick, first completed rise, first completed fall and first depart, plus a tick count every 5000 — the sweep that showed 6 of 12 recordings move a lift and 5 exercise all three states |
| `KAROO_BLOCK_DIAG=1` | logs the slide's first tick, first vacate, first completed advance, first completed retreat and first depart, plus a tick count every 5000 — the sweep that showed all four paths are exercised by 5 of 12 |
| `KAROO_FOESTEP_DIAG=1` | logs the foe step's first tick, contact, tile consume, chase direction, turn-table entry, return-to-post and frozen foe — the sweep that found three of its paths are reached by no recording at all |
| `KAROO_SPLINE_SELFCHECK=1` | checks `EvalBezierPath` against the closed-form Bernstein polynomial for degrees 0–3 inside the DLL, on the real heap under the real ABI, and logs a line per case plus a PASS/FAIL total.  Values are derived independently, not captured, so it is an assertion rather than a snapshot.  **Watched to fail**: under `KAROO_SIM_FX=splinerev` it reports 5 failures with expected and actual, and correctly stays silent on the cases that are symmetric under reversal (a constant path, and the midpoints of the two symmetric test curves) |
| `KAROO_SPLINE_DIAG=N` | census of the spline class every N evaluations — evaluations, empty-list evaluations, the largest control-point count seen, adds, purges, ctors, dtors and debug draws.  **N is used, not just tested**: a fixed interval hid the difference between a recording that evaluates twice and one that evaluates 456 times on this census's first run.  Reports max points = 13 everywhere, one short of the 14 at which the original's factorial binomial overflows, and `draws=0` on every gate |
| `KAROO_REMOVE_DIAG=1` | logs the first foe removal (`foe.cpp`), bomb removal (`bomb.cpp`), sound release, virtual destructor call and compaction shift, plus a count every 500 — and, since the allocator moved in beside them, a line per ID claim carrying the count, the ID issued, the number of gaps the scan saw, the lowest of them, and a running tally of how often lowest and issued disagree |
| `KAROO_SPAWN_DIAG=1` | logs the first foe spawn, bomb spawn, high type, kind-2 and kind-3 foe and sound acquisition, plus a count every 500.  Under `levelreport.py` it also censuses the whole foe-type alphabet across all 80 levels and names every level carrying a type above 0x64 — that census is how `freeze03` and `enemyfactory` were chosen |
| `KAROO_TILEQ_DIAG=1` | logs the first call to each of the four tile queries and the first successful RESULT from each, plus a call count every 5000 — how to tell "this recording never calls the query" from "it calls it and never gets a hit" |
| `KAROO_PLACE_DIAG=1` | logs the first lift spawn, the first failed allocation, a spawn count every 500, and **every slide and bridge spawn with its kind/axis** (`SCAN-U` / `SCAN-V` / `no-scan`) — the census that showed `slideaxis`'s single failure is weak coverage rather than the maximum available |
| `KAROO_RESET_DIAG=1` | logs the first call to `ClearGameState` and each of the four purges, the first sound release, virtual destructor, foe drain and enemy drain, plus every **LIVE** purge — one entered with a nonzero count, the only kind that destroys anything.  That last counter is what distinguishes "the suite never tears down a populated level" from "it does, and the control still cannot see it" |
| `KAROO_MENUSTACK_DIAG=1` | logs the first menu-stack push, pop and rewind and then EVERY call with running counts and max depth — a census, not a sample, because the whole family is called under a dozen times per recording |
| `KAROO_LEVELPARSE_DIAG=1` | logs every call to EITHER level loader with the level name/number, map result, `+0x10` flag and script counter, plus the bonus peek and the first extra-object sound release — the diag that revealed `ParseLevelFiles` and `OpenLevelFile` are duplicates and that recordings only execute the latter |
| `KAROO_SETUP_DIAG=1` | logs each `SetupLevelObjects` call with the map extents and the full per-kind census — crystals, total, bridges, teleports, lifts, slides, breakables, foes, free bombs, timed items, switch max |

| `KAROO_ANI_DUMP=<path>` | appends `<path> table=<fnv1a>` per `.ani` loaded (`ani.cpp`) — the whole 0x180-byte table hashed, for comparison against an independent parse, and the only observation of the animation data either gate can make.  A `levelreport.py` run touches 8 of the 24 shipped files |
| `KAROO_THEME_STRUCT_DIAG=1` | the populated theme block (`theme.cpp`, ASSET_PLAN Phase 5).  When `Theme_Load` finishes a `.thm`, dumps the `ThemeAssetBlock` at `0x46c890` through `theme.h`'s types as `THEME_STRUCT:` lines: every slot's records (kind, mesh, position/scale/rotation, flags, oscillation, pump, explode) and their sub-objects (condition, texture, blend, address mode, effect), the images, text colours, fog flag, side height and sky faces.  Implausible values are tagged `SUSPICIOUS`.  Built to check the layout against live memory before the loader was replaced: `bridge01` (Forest + Space) gave 571 lines, 0 suspicious, cross-checked against the `.thm` sources.  Read by value; inert unset |
| `KAROO_JJS_DIAG=1` | logs every script line the interpreter runs, with its command.  14 of 16 recordings run 13–27 lines (`splinexyz`, `observe`, `setcam*`, `wait`, `initwave`, `playwave`, `text`, `distance`, `gotoxyz`, `fromhere`); `protectionstart` and `switchfoe` run none; **none runs `movetoxyz`** |
| `KAROO_LEO_RECDUMP=<path>` | appends every `.leo` record built, field by field, plus an FNV-1a hash of each record's fields laid end to end, the original's 0xf40-byte record (records `0..objectCount` inclusive).  `levelreport.py` sets it and compares against `tests/levelreport/LeoRecords.txt`, captured from the ORIGINAL `ParseExtraObjectEntry` before the replacement: 32 loads, 327 records, identical after it |
